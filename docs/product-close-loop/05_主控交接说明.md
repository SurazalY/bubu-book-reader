## 3. T3.2 批量导入：必须知道的陷阱

这一节是前一任写好但尚未执行的任务要点，逐条都有代价背书，不要跳过。

### 3.1 先备份，且不能用文件复制

数据库是 **WAL 模式**，未 checkpoint 的数据在 `-wal` 文件里，**单独复制 `.sqlite` 不是有效备份**。用 `VACUUM INTO '<路径>'` 或 SQLite 备份 API。备份后要验证能打开且关键表行数合理。命名参照 `server/data/` 下已有的 `readmate.sqlite.phase0-backup`、`readmate.sqlite.pre-phase2-backup`。

### 3.2 book-001 上挂着真人的真实阅读数据 —— 已裁决：T3.2 跳过它，只导另外 48 本

**库状态已于 2026-08-17 19:00 只读核验（前一任亲自查的，不是推测）**：`books` 表只有 1 行 `book-001`（`published`），`book_versions` 只有 `book-001-trusted-v1`（`trusted-baseline`）。**book-028 并未导入**，之前"可能已导入"的说法是错的。所以 T3.2 的实际输入是 **48 本全新导入 + book-001 跳过**。

真人的阅读记录通过 `book_version_id = book-001-trusted-v1` 引用 book-001（`reading_summary_sessions` 7 行、`reading_page_coverage`、`reading_progress`、`reading_daily_book_summaries`），**重导它是全 Phase 3 唯一有数据事故风险的动作**。

**裁决：跳过 book-001，不要重导。** 依据是它当前入库状态已满足 T3.3 的全部五类断言（同一次只读核验确认）：

在导入汇总表里把 book-001 记为"已存在且已核验合规，按裁决跳过"，T3.3 照常把它纳入断言范围（只读，安全）。

### 3.3 book-001 / book-028 的包是复用的，先验确定性

T3.1 汇总里 `skippedExisting = true` 的恰是这两本（book-001、book-028），复用了 Phase 1 的旧产物，未用当前打包器重建。若当前打包器产出与旧产物不同，那么 book-028 会以一个"旧格式包"被导进库，而 book-001 的入库内容与当前打包器输出不一致。

先用 `--force` 重建这两本（**打包只写包目录、不碰数据库，安全**），把新的 `manifestSha256` 与 T3.1 汇总比对：

- book-001 应为 `05941212b7f9cf33b6d7d52042c41cfb9bfad523e97c676fe96e502a902842d6`
- book-028 应为 `e0010463288f24fb31d2e595c14151b831404e1df9de6f4ca9f5e697b67b6570`

book-028 若不一致，用重建后的新包导入即可（它还没入库，无风险）。**book-001 若不一致，停下来报告用户，不要自行决定重导**——见 §3.2 裁决。

### 3.4 其余要点

- 导入必须带 `--accept-trusted`（决策 D1：OCR 是可信输入）。所有包 `quality.status = trusted-baseline`。
- **book-031 导入前再断言 `pageNo` 1–161 连续**（T3.1 已确认，仍按清单要求复验）。
- **npm 11 会吞掉 `--` 后的参数**，直接用 `node server/db/import-book-package-v2.js ...`，不要用 `npm run xxx -- --flag`。
- `--public-root` 必须与运行时 `PUBLIC_ASSET_DIR` 一致。`.env` 里配的是 `PUBLIC_ASSET_DIR=../public`（注意：`server/app.js` 的代码默认值会退到 `dist/`，与 README 早前写的 `public/` 不一致，这条踩过）。
- **逐本独立、失败续跑**：某本失败不中断整批，记录原因继续，最后如实列出成功/失败。
- **不得对 OCR 做任何质量验收或修正。** 不要因为某页文本"看起来不对"就改它或报缺陷。
- 磁盘：包产物已占 3.36 GB，导入会往 `public/books/` 复制，`npm run build` 还会往 `dist/` 复制约 3.3 GB。D 盘当时可用 231 GB，够用但要留意。

## 9. 用血换来的教训

1. **服务端改完不重启等于没改。** Node 不热加载。曾因此让用户白读 6 分钟。
2. **单元测试全绿不等于线上生效。** D-15 的首版修复在停滞判定 SQL 里带了 `status = 'open'` 过滤，而僵尸页重新获取租约会把会话标成 `closed`，判定永远查不到行。server 196/196 全绿，线上判定从未触发。是去数据库看续期计数才发现的。**回归用例必须按真实生产路径建模，不能只测纯函数或组件内部实现。**
3. **agent 自己开的浏览器标签页会脱管，并持续占用业务资源。** 一个下午遗留的阅读器页面每 60 秒续租一次，把租约钉死近三小时，导致真人连监测会话都建不起来，三轮复验全败。**验证完必须关页。**

   **2026-08-17 19:41 更正，这条比原先写的更严重**：该标签页**在用户的 Cursor 界面里根本看不到、也无法关闭**（用户原话"这个根本就没有啊，至少对我是透明的"）。`browser_tabs list` 在主控会话里返回空，说明它属于别的 agent 会话的浏览器上下文，已完全脱管。**结论：「用完关页」不能作为可依赖的防线，因为人类没有执行它的手段。** 因此不要把任何缺陷的收尾寄托在"让用户去关那个页面"上。

   **可复用的应急手段（本次实测有效）**：轮换 `.env` 里的 `SESSION_TOKEN_SECRET` 并重启后端，即可让所有既有会话签名失效——脱管页面从此无法认证，既不能续租也不能重新获取租约，且**完全不触碰业务数据**（实测四张阅读事实表前后一致）。代价仅是所有人需重新登录一次，演示密码不受影响。比去猜哪个进程该杀安全得多。
4. **排查"客户端仍在活动"要先用连接归属证据定宿主进程，别先让真人关浏览器。** 当时误判为"用户 Chrome 后台残留"，用户白关三次、杀掉 29 个 chrome.exe 仍无效。真凶是 Cursor 内嵌浏览器里的页面。有效手法：`Get-NetTCPConnection` 观察前后端端口的客户端端口是否连号成对，再查 socket 归属进程及其父进程。
5. **主控别自己钻代码。** 前一任被用户当场指出过"你怎么一直在自己探索"。允许的直接操作只有读计划文档、git 检查点、单文件/单条只读查询级别的抽查。
6. **裁决要留痕。** 所有决策写进台账或计划文档，不要只存在于对话里。
