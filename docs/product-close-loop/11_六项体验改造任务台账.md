## 二、守卫与实现的配对纪律

本项目已有实证：Phase 4 最危险的越权缺陷是由**独立的对抗式守卫 agent** 攻出来的，写实现的 agent 自己没发现，主控抽查也没发现。因此本轮沿用同一做法。

对每一对任务：

1. **先派守卫 agent**，它只写测试，跑起来应当是**红的**（因为实现还不存在）。它必须在报告里说明每条测试红在哪一行、红的原因是不是"功能未实现"而不是"测试自己写错了"。
2. **再派实现 agent**，简报中明确写：**不得修改守卫 agent 新增的任何测试文件**。
3. 实现完成后守卫应当**全绿**。若仍红，一律按实现越界处理，回退重做，**不许改测试消红**。
4. 唯一例外是每个任务简报里「授权同步更新的既有测试」小节逐条列出的文件与行号——那些是契约变更的必然结果。改动它们必须在任务报告里逐条说明理由。

## 四、风险登记

| 风险 | 影响任务 | 说明与对策 |
|---|---|---|
| 「年级」被误当成 `grade_id` | T4 全部 | 系统里 `grade_id` 是入学届。一旦搞混，同一届学生会被拆到不同年级、或升年级后统计错位。对策：G4-1 与 G4-2 两条守卫专门盯这件事 |
| 阅读统计的响应字段被前端精确白名单锁死 | T4-2 | 在 `class` 对象上多加一个字段就会让前端解析与后端根字段冻结用例一起红。对策：契约要求多班档**合成同形对象**，不改字段数量 |
| 汇总时把各班百分比相加 | T4-2 | 这是统计口径的经典错误。对策：G4-8 用两个分子分母不同的班做交叉验证 |
| 登录 helper 改动波及大量 HTTP 测试 | T2-2 | 对策：只改 helper 本体，不逐个改用例；且把 T2 排在最前，减少与其他任务的冲突面 |
| 明文密码泄漏面扩大 | T3-2 | 对策：明文只存 `issued_temp_passwords` 一张表、只存教师签发的临时密码、学生自改即删、审计与日志一律禁明文（G3-9） |
| 删除 `Settings.jsx` / `console/pages/Me.jsx` 触发源码扫描类测试 | T6-3 | 对策：简报里已逐条列出授权修改的文件与行号，其余黑名单条目一律冻结 |
| 校徽脚本抠图边缘脏 | T5-0 | 对策：明确首选人工描 SVG，脚本仅作预览；验收必须在真实半透明背景上目视 |
| 实现 agent 用「改测试」代替「改实现」 | 全部 | 对策：守卫与实现分派给不同 agent；实现方简报里写死不得修改守卫；授权修改清单精确到行号，清单外一律视为越界 |
