### 步 1：发布/下架往返（可立即做，无前置）

用**李老师**登录控制台 → 教学 → 书库，对任意一本书点下架。然后用**林小竹**登录学生端，确认书架上该书消失、直接访问它的详情/阅读页也进不去。再回李老师那里重新发布，确认林小竹的书架恢复。

### 步 2：跨班隔离——**这一步现在被卡住了**

原计划：校长新建一个空的 B 班，把某本书的可见范围限定到 B 班，然后确认林小竹（三年级一班）看不到它，恢复后又看到。

服务端接口是好的（L3 用真实 HTTP 实测 `POST /classes`、`POST /students` 均 201），缺的只是前端接线。

**所以这一步必须走 HTTP 直连业务库，需要用户单独授权**——此前所有验证都严格只用临时库或 `VACUUM INTO` 副本，一次都没写过业务库。上一任主控向用户提出了四个选项（只建空班 / 建班加学生 / 不写库把该条标"因环境未验证" / 用户自己执行），**用户尚未选定**，接手后请重新确认。

**一个能省事的事实**：负向演示只需要一个**空的** B 班就够了。校长把书限定到空的 B 班 → 林小竹立刻看不到 → 恢复 → 又看到。不需要 B 班里有学生。正向侧（B 班学生能看到）L3 已在副本上验过。

**另一个必须知道的约束**：李老师是 class 范围，她**只能**把书限定到自己班，把书限定到 B 班这一步**必须校长做**。李老师尝试授权给别班会得到 403——这是 F-1 收紧后的**正确**行为，不是缺陷。

若用户批准写库，建班用校长身份调 `POST /api/v1/classes`，**必须带 `Idempotency-Key` 头**（本项目所有写接口都要），带 `readmate_session` Cookie 与 `X-Workspace-Id: internal-demo-school-workspace`。

## 三、Phase 4 交付了什么（供归档时逐条核对）

### 七个原定任务

T4.1 发布/下架 HTTP（`publish`/`unpublish`，走 `book.publish` + Idempotency-Key + 审计）；T4.2 教师权限（`teacher` 与 `grade_manager` 加 `book.publish`，别名 `class_teacher`/`grade_group` 经 `roleAliases` 自动生效）；T4.3 可见范围领域逻辑（四入口统一过滤，不可见一律 404）；T4.4 可见范围 HTTP（`GET`/`PUT visibility`，校验班级属本组织且在操作者授权范围内）；T4.5 教师端 UI（发布状态与操作、班级可见范围面板、教师书库年级筛选）；T4.6 学生书架年级筛选；T4.7 测试。全部落地。

### 计划外但必要的三块

- **D-14**：`getBookAsset` 原本**完全没有鉴权**，同一工作空间内任何登录用户都能取到任意书的封面与源 PDF。这是 T4.3 的真实前置——不补它，"可见范围"就是空的。Phase 4 的实际起点比 `03` 文档描述的靠前得多。
- **D-09 / D-10**：详情页封面冷请求取不到（裸 `<img>` 带不了 `X-Workspace-Id` 头必然 400）；资产响应带 `max-age=3600` 且无 `Vary`，导致一次带头 fetch 会为同一 URL 预热缓存、**掩盖鉴权失败**（D-09 曾因此被误判为通过），且授权结果被缓存一小时——取消发布后学生浏览器仍能读到源 PDF。已改为封面 `no-store`、其余一律 `private, no-cache` + ETag 的 fail-safe 默认，并加了防绕过静态扫描守卫。
- **F-1 / F-4**：见下节。

### 独立验证方攻出来的四个洞

Phase 4 用了一个只写测试、不改实现的独立验证方（`tests/server/http/book-visibility-guard.test.js`，18 条对抗式用例）。它攻出：

- **F-1（已修）真实越权**：班级教师被拒绝"授权给别班"（403）之后，改发 `{"scope":"organization"}` 就能 200——把书对全校放开，等于白拿刚被拒掉的权限，还顺手抹掉校长给别班设的授权。根因是授权范围校验**只校验新增哪些班、不校验移除哪些班**。已加对称校验（移除某班的授权时该班也必须在操作者范围内），并对悬空 grants（班级已停用/已删除）豁免，否则那些书会永久无人可改。
- **F-4（已修）逃生通道失效**：一行 `grantee_type='user'` 的 grants 会让书对所有学生消失，而 `PUT {"scope":"organization"}` 删不掉它。已改为 organization 的 DELETE 清除本书全部版本上的**全部类型** grants。
- **F-2 / F-3（未修，登记为 D-22 / D-23）**：见下节。

新增的 `tests/server/http/book-visibility-revoke-guard.test.js`（7 条）正面覆盖 F-1/F-4 的新规则。

## 四、已知未修的残余缺陷——**这是接手后最该记住的一节**

**班级可见范围目前不是密不透风的。** 契约点名的四个入口（书目列表、读页、资产、AI 引用）已封死并有 25 条守卫用例锁着，但存在三条残余泄露路径，都是上一任主控**主动决定本期不修**的：

- **D-21 社区引文泄露书页原文**：`getPost` 返回的 `quote.text` 最长 2000 字、投稿时经校验确为该书页原文，但**读取时没有任何可见范围过滤**。B 班学生引用一本限定给 B 班的书投稿 → 过审 → **A 班学生在社区里读到该书原文片段**，同时拿到 bookId 与页码。**这是内容泄露，不只是存在性泄露**，是目前已知的唯一残余内容泄露路径。不修的理由：触发需人工审核放行，且正确修法要先定产品语义（投稿时拦 / 读取时过滤 / 已过审旧帖是否追溯）。
- **D-22 `GET /assignments` 泄露书名与版本 id**：只泄露元数据不泄露正文。**它是 D-23 的前置**——学生正是从这里拿到 `bookVersionId` 的。
- **D-23 `POST /reading/lease` 既不过可见范围也不过发布状态**：学生拿 D-22 得来的 versionId 对不可见书或草稿书申请租约都得 200。不泄露正文，但**学生可以对一本自己打不开的书累计阅读时长，污染阅读统计**——而"阅读被记录"正是本产品的核心承诺。**不修的关键理由**：租约 TTL 与续租路由属项目冻结契约，是 D-11/D-15/D-17 三次复发的重灾区，验收前夜动它风险过高。

**D-22 与 D-23 应当一并规划**，单修一个意义不大。

另有两条运营能力缺口：**D-20**（建班后无法把已有教师加进去，连服务端接口都没有；`role_assignments` 绑工作空间，所以"教师属于哪个班"不是一条成员关系而是"她在该班工作空间有 teacher 角色分配"，这是设计难点）、**D-24**（前端班级与账号管理整块是演示壳，见上文步 2）。

## 六、给接手主控的硬规则与踩过的坑

### 硬规则（来自用户，逐条都是红线）

- **主控不写业务代码、不跑测试构建、不直接探索代码库。** 一切实现派子 agent。主控可以读文档、做最小抽查。
- **不推不提交，不开浏览器。** 浏览器操作全部由用户本人执行。本项目曾因 agent 开的标签页脱管、持续占用业务资源而堵死近三小时。
- **不得宣称"验收通过"**，必须有真实运行证据。
- **阅读计时是冻结契约**：表、schema、指纹算法、租约 TTL、续租路由一律不动。
- **决策必须留痕**，写进 `evidence/phase4/decisions.md`。

### 派子 agent 的经验（Phase 4 实打实的教训）

- **每个任务的 prompt 里必须重申完整禁令**，尤其"不得 `git checkout`/`reset`/`stash`/`clean`"——工作区里堆着多个 agent 的未提交成果，清掉找不回来。
- **子 agent 会越界做"顺手的清理"**。有一个以"不得出现完成度"为由删掉了既有 UI 里的阅读安排完成率（那是班级管理指标，不是个人阅读进度，且契约限定的是**新增**界面）。已驳回并还原。硬契约是约束新增的，不是授权在无关范围内做清理。
- **子 agent 会留下"休眠缺陷"**。D-10 第一版把封面改成 `no-store` 但其余类型保留 `max-age=3600`，等于把缺陷改成潜伏态。要求改成 fail-safe 默认后才通过。
- **要求每份报告分「实测」与「推断」两栏**，这一条抓出了大量问题。
- **子 agent 的高危报告也可能是误报**。L3 以【高】级别报"`express`/`dotenv` 未声明、验收当天重启后端会起不来"，实际是它只看了仓库根——本项目前后端**分开声明分开安装**，`server/package.json` 两者都声明了且都装好。**多包仓库判断依赖缺失必须逐包检查。**
- **npm 11 会吞掉 `--` 之后的参数**，单跑一个测试文件要直接 `node --test <路径>`。
- **独立验证方的测试文件是它的资产**，实施方不得随意改动。Phase 4 有三条用例因 F-1/F-4 收口需要更新，全部经主控逐条授权，理由记在 `decisions.md`。新增用例应放**新文件**，否则"哪条断言是谁写的"不可查。

### 一个方法论教训（主控自己踩的）

改 `toBook` 这类适配器层字段前，**必须把消费方的引用链查到底**，不能靠组件名和跳转路径推断归属。上一任主控曾误认为 `src/components/ui.jsx` 的 `BookCard` 在学生端运行时路径上并据此派了修复任务，复核后发现它只服务旧站演示数据；若改下去会造出「三年级 年级」这种新缺陷。已中断该任务。

## 七、后续两个大改动的交接

用户已提出目标权限模型：**年级主任+校长控制班级范围（一个班有哪些学生和老师），语文老师从书库中选择她需要的书**。用户已裁决「先验收当前语义，再重设计」。

这个目标拆成两件独立的事，**不需要推倒 Phase 4**：

- **可见范围默认翻转**（薄）：现在是"无 grants = 全组织可见"，目标是"默认全闭、教师挑选投放"。存储层（`book_access_grants` 的 `(book_version_id, class, classId)` 三元组）两种模型完全共用；四入口过滤、`class-scope.js` 的授权范围推导、F-1 对称校验、发布/下架全部照用。默认值在 `visibility.js` 的 `isBookVisibleToAudience` 里就是**一行**。**唯一有风险的一步是数据迁移**——翻转瞬间 49 本书会对所有学生消失（真库 grants 现为 0 行），必须配一次批量写入保持翻转前后一致。附带好处：翻转后 F-4 那一整类问题自动消失，逃生通道概念可删。最大工作量在测试夹具（25+10 条用例的前置状态都建立在"默认全开"上）。
- **班级成员管理**（厚，基本从零）：见 D-20 + D-24。**与 Phase 5 零文件重叠，可完全并行。**

**排期建议**：Phase 5 先做（它修的全是用户当场能感知的痛点：学生退不出登录、切文字模式刷新就忘、摘录跳转落错页、以及 D-06 文字模式长页正文被裁且**根本读不到**属内容丢失）。可见范围翻转**不要与 Phase 5 并行**——两者都动 `catalog.js`（该文件 Phase 4 已 +214 行，是热点），且翻转带迁移，混在一起出问题分不清是谁的。班级成员管理可以随时并行。

D-06 的修法涉及产品取舍（页内滚动 / 自动缩字号 / 加展开），**需用户裁决**，不在 T5.1–T5.5 范围内，不阻塞 Phase 5 开工。
