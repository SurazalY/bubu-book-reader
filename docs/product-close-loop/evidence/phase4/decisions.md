## 八条裁决

### 决策 P4-1：`book.publish` 授予 teacher 与 grade_manager 两个角色

`06` §3.1 更正三指出 `03` 文档未写 grade_manager，要求向用户确认。裁决：**teacher 和 grade_manager 都加**。`school_admin` 与 `platform_ops` 原本已有，不变。`permissions.js` 里不存在 `class_teacher` 角色，无需处理别名。

### 决策 P4-2：下架/再发布实验用 book-005

真人验收要做「下架某书 → 学生书架消失 → 再发布恢复」，这会修改 `books.status`。**用 book-005，完全避开 book-001**——book-001 上挂着真人的真实阅读数据（`book_version_id = book-001-trusted-v1`）。book-005 是嵌套 source.json 的书，Phase 3 抽查过，状态已知。

### 决策 P4-3：机器实测不碰业务库

依据硬规则 4（不得擅自向 `server/data/readmate.sqlite` 写入，需要可写库就复制副本到临时目录）。裁决：

- **机器实测（L3）全部在 `VACUUM INTO` 出来的临时数据库副本 + 独立端口的临时后端实例上进行**，由主控自行起停，全程不碰 5191 与业务库。
- **业务库上的写操作（建第二个班、加班级成员、设可见范围、下架/再发布）全部由用户在真人验收时通过界面完成**，agent 一律不做。

### 决策 P4-4：源 PDF 缓存退化时的兜底口径（预先授权）

D-10 定档方案是封面 `private, no-store`、源 PDF `private, no-cache` + `ETag`。若实测发现源 PDF 在 `no-cache` 下退化为整本重传（平均 67 MB／本）：

- **允许**改用语义等价的 `private, max-age=0, must-revalidate` + `ETag` 再测。
- **不允许**自行放宽成 `max-age` 大于 0 的任何值。若等价写法仍退化，**停下来向用户报实测数据**，不得自行裁决。

### 决策 P4-5：教师/管理角色可取本组织任意发布状态书籍的资产

**这是一处鉴权边界的放宽，由用户明确批准。**

冲突来源：决策 D3 规定「教师/管理角色在控制台书库始终可见本组织全部书（否则无法管理）」，但 `getBookAsset` 的 SQL 里有一条对所有角色生效的 `AND book.status = 'published'`（`catalog.js` 185–198）。后果是教师一旦下架某书，教师端书库里该书的封面立即 404 变占位图，而教师还要在那张卡片上点「重新发布」。

裁决：**放宽**。教师/管理角色可取本组织任意状态书籍的资产（封面与源 PDF 均可）；**学生仍严格限 `published` + 班级 grants**。

落地要求：必须补守卫测试断言「学生请求 draft 书的资产仍然 404」，防止放宽被写成对所有角色生效。

### 决策 P4-6（第一版，**已作废**）：校长建第二个班时把 internal-teacher-li 一并加为成员

冲突来源：`06` §3.1 更正三已确认建班必须用校长账号 `internal-principal`（老师是 class 范围，`POST /classes` 要求 school 范围的 `class.manage`）。但 B-4 第三条要求「教师设置可见范围的 UI 只列出该教师有权限范围内的班级」，校长新建的班老师看不到，验收路径会断在这一步。

第一版裁决：校长建班时把 `internal-teacher-li` 一并加进新班，由老师本人设置可见范围。

**该版本作废，原因见 P4-6R。**

### 决策 P4-6R（生效版）：校长做两个动作，教师侧照常验；缺失能力记为 D-20

**作废第一版的实测依据**（主控亲自检索确认，非转述）：

`server/` 里唯一写 `class_memberships` 与 `role_assignments` 的运行时代码在 `server/domains/identity/repository.js:188-210`，属于 `POST /students`（新建学生账号），`membership_role` 硬编码为 `'student'`。**产品里不存在任何 HTTP 接口或领域函数，能把一个已存在的教师加进一个已存在的班级。**

更深一层：教师的管理权来自 `role_assignments`（`role_code` + `scope_type='class'` + `scope_id`），不是 `class_memberships`；且 `scopeAllows` 要求 `grant.workspaceId === authContext.workspaceId`。`POST /classes` 会连带新建一个 class workspace，教师在该 workspace 上没有任何 role assignment，所以即便补了成员关系也未必能管理该班——要真正生效需要补两行。

**生效裁决：**

1. Phase 4 只做 T4.1–T4.7 + D-09/D-10/D-14，**不动权限模型**。
2. 真人验收时**校长只做两个动作**：建一个空班 B、把 book-005 的可见范围限定到 B 班。教师侧该验的（下架 book-005 让学生书架消失、再发布恢复、把书限定到自己的三年级一班而学生仍可见）全部由 `internal-teacher-li` 本人做。
3. 「建班后无法把已有教师指派到班级」记为**新缺陷 D-20**，留给后续单独立项。理由：它属于身份管理能力，不属于书籍可见范围；且演示脚本给一位教师绑班要同时写 workspace 成员、班级成员、role assignment 三样，少写一样就会造出权限残缺或越权的账号，值得单独设计。同期既改鉴权边界又改权限模型会导致故障无法归因。

**演示组织的实测构成**（`bootstrap-internal-demo.js:180-256`）：一个班 `internal-demo-class`（三年级一班）、一个学生 `internal-student`（林小竹）、两位教师 `internal-teacher-li`/`internal-teacher-wang`（**两人挂在同一个班**，`role_code` 均为 `'teacher'`）、一位校长 `internal-principal`（`school_admin`，school 范围）。

**一处虚惊已排除**：`bootstrap-internal-demo.js:203` 的 `code: 'class-teacher'` 是 **workspace 的 code**，不是角色码。真正的 `roleCode` 取自同文件 180–182 行，两位教师都是 `'teacher'`。所以 T4.2 把 `book.publish` 加在 `teacher` 上对演示教师**确实生效**。

### 决策 P4-9：业务角色扩展（年级主任 / 学科组组长）不在 Phase 4 落地

产品负责人提出「校长的权限应扩散到年级主任 / 学科组组长」。处置分两半：

**年级主任这一半，本期即落地**，不需要扩大范围：`grade_manager` 就是年级主任，已是现有五个角色之一，P4-1 已给它 `book.publish`。再加上 P4-10 的实现口径，年级主任天然获得跨本年级设置可见范围的能力。

**学科组组长这一半，本期不做**，现有模型装不下，缺的是两个维度：

1. scope 是一条包含链（own ⊂ class ⊂ grade ⊂ school ⊂ platform），且写死在 `role_assignments` 的 CHECK 约束里（`005_organization_roles_and_idempotency_fencing.sql:77`）。学科组是**正交**维度（语文组横跨多个年级、只覆盖一科），无法用 `scope_id` 表达。
2. 书目元数据里没有学科字段，「学科组组长只管本学科的书」缺少过滤依据。

两处都要动 schema 与权限评估器，属独立项目。已派只读设计分析，产出 `docs/product-close-loop/design/role-model-extension.md` 供决策，**不含任何已实施改动**。

### 更正记录 C-1：`06` §3.1 更正三的前提有误（别名表是存在的）

`06_Phase4交接说明.md` §3.1 更正三写「没有 `class_teacher`，不需要处理别名」。**前提错，结论对。**

实测（主控亲自读源码，`server/domains/identity/permissions.js:127-137`）：

```javascript
const roleAliases = {
  class_teacher: 'teacher',
  grade_group: 'grade_manager',
  grade_admin: 'grade_manager',
  platform_operator: 'platform_ops',
}

function hasAction(policy, roleCode, action) {
  const normalizedRole = roleAliases[roleCode] ?? roleCode
  return (policy[normalizedRole] ?? []).includes(action)
}
```

`roleActions` 里确实只有五个键（这部分 `06` 没写错），但另有一张 `roleAliases` 表，别名在 `hasAction` 里集中归一化。

**对 T4.2 的影响：做法不变。** 给 `teacher` 加 `book.publish` 后，`role_code = 'class_teacher'` 的用户自动获得，无需额外处理。

**一个连带扩散，需要留痕**：`grade_group`（教研组）是 `grade_manager` 的别名，因此决策 P4-1 给 `grade_manager` 加 `book.publish` 之后，**教研组角色也会自动获得发布权**。方向上与产品负责人「学科组组长理应享有这些权限」的诉求一致，已告知，不视为缺陷。

### 更正记录 C-2：`grade_manager` 这一半无法真人验收，只能标 L2

`bootstrap-internal-demo.js` 的演示数据里**没有 `grade_manager` 账号，也没有 grade 范围的工作空间**（只有学生 `internal-student`、两位 `teacher`、校长 `school_admin`、平台运维）。

- **不能**在真人验收中验证 → **不得标 L4，不得写「通过」**

最终报告必须如实分开标注 `teacher` 与 `grade_manager` 两半的验证等级。

### 决策 P4-11：社区帖图缺 coverUrl 时，允许以「只加字段」的方式改社区后端

产品负责人授予自由裁量（原话「可以按你自己想要的改吧……只要能稳定把事做的漂亮就行」）。主控选定的口径：

- **允许**在社区接口的现有查询里关联书目投影，**新增**一个封面地址字段。
- **不得**修改或删除任何已有字段。理由与 B-3 既有契约一致（新增字段允许，改动/删除已有字段不允许）：新增字段几乎不可能影响其它调用方，而改动既有字段会波及无法一次看全的消费者。
- 若出现「必须改动既有字段才能做到」的情况，**不硬做**，把社区帖图留到次日由产品负责人裁决，其余部分照常交付。
- 无论如何**不得**把封面复制到 `public/covers/`（违反 B-2 §6）。

### 决策 P4-12：教师发布权限实测不通过时的分流规则

要求 T4.1 必须用真实 HTTP 链路实测「class 范围的教师能否发布」，不许推断。若实测不通过：

- **若根因是新路由自己把 resourceScope 构造错了**（与 `POST /classes` 把资源写成纯 school 形、导致年级主任被拒属同类 bug），**允许**按 `workspaceResourceScope` 正确构造后重测。这是修 bug，不是放宽权限。
- **若根因是权限模型本身不支持 class 范围的教师发布本组织的书**，**停下来等产品负责人裁决，不得自行放宽权限模型**。

### 决策 P4-13：收窄可见范围时必须真实检查引用，不能只放静态文案

B-4 原文：「课堂锁书/阅读安排引用了对某班不可见的书属于边界情况：本期只需保证『设置可见范围时给教师明确提示』，不做级联清理。」

裁决：**「明确提示」取强解**——保存前真实查询这本书是否被课堂锁书或阅读安排引用，有则提示具体影响（形如「还有 N 个安排引用本书，收窄后这些班的学生将无法打开」）。

**仍然不做级联清理**（B-4 明确不要求，且级联删除他人安排风险过高）。

### 决策 P4-10：可见范围的班级列表按操作者授权范围动态取

B-4 第三条原文是「教师设置可见范围的 UI 只列出该教师有权限范围内的班级」。**不得**把它实现成硬编码的「教师自己的班」，而要按操作者的授权 scope 动态解析：

| 操作者 scope | 可选班级 |
|---|---|
| class | 自己的班 |
| grade | 本年级全部班 |
| school | 全校全部班 |

这既是 B-4 的正确读法，也顺带满足了年级主任的业务诉求，且不扩大 Phase 4 范围。

**附带的落地要求（一个已识别的坑）**：现有前端没有真正的「列班级」接口，`src/api/stage4.js:77-82` 的 `listClasses()` 是调 `GET /students` 再按学生分组拼出来的。**一个刚建好、尚无学生的空班用这个办法列不出来**——若照抄现状，验收当天教师端下拉框里看不到新建的 B 班，可见范围验收会直接卡死。因此 T4.4 必须提供一个按授权范围返回班级的真实接口。

### 决策 P4-7：社区帖图本期一起改造

冲突来源：`design/protected-asset-consumption.md` §决策 3 把社区帖图列为 P2 可推迟；但 `06` §9 第 6 类守卫测试把「`PostCard.jsx` 不再出现 `covers/${book.id}.jpg` 字面量」写成硬要求。两份文档对不上。

### 决策 P4-8：后端 5191 全程只重启一次

Node 不热加载，服务端改完必须重启。裁决：**全程只重启一次，时机是用户开始真人验收之前，由主控派 shell 子 agent 执行，动手前先在聊天里告知用户。**

理由：机器实测跑在数据库副本 + 独立端口的临时实例上（决策 P4-3），不需要 5191，因此不必每轮改动都重启。重启会踢掉当时所有登录中的会话。

### 决策 P4-14：教师资产放宽的边界收在 `getBookAsset`，`getPage` 不动

决策 P4-5 批准「教师/管理角色可取本组织任意状态书的资产」。落地时明确边界：

- **放宽**：`getBookAsset` 对教师/管理角色去掉 `status='published'` 与 grants 过滤，组织隔离保留。
- **不放宽**：`getPage` 的 `b.status='published'` 对所有角色维持原样。教师端阅读器不在本期范围（`06` §11）。

由此产生一处可察觉的不对称：教师能下载草稿书的源 PDF，却读不到它的 OCR 文本页。这是为了把改动面压到最小而接受的，不是遗漏。若后续要对齐，应作为独立任务处理。

**配套守卫**：必须有「学生取 draft 书资产仍 404」的测试，防止放宽被写成对所有角色生效。

### 决策 P4-15：可见范围复用既有权限动作，不新造

`GET /books/:bookId/visibility` 用 `book.read`，`PUT` 用 `book.publish`。**不新增权限动作**——新动作意味着新的权限面和新的分配路径，而本期并无哪个角色需要「能设可见范围但不能发布」这种组合。

### 决策 P4-16：`getBookVersionAssets` 作为潜在第五入口排查

B-4 点名的过滤入口是四个，但 `catalog.js:167-183` 还有一个 `getBookVersionAssets`，SQL 口径与 `getBookAsset` 相同。已要求实施方查明它是否学生可达：可达则按第五入口一并过滤，不可达则在报告中给出证据。**不允许以「契约只写了四个」为由跳过排查。**

### 决策 P4-17：grants 读侧按「书」聚合，不按字面的版本级语义

实施方 T4.3 提出并已落地一处对字面契约的加固，主控**裁决保留**。

- **字面契约**：B-4 写的是「grants 以 `book_version_id` 为键」。
- **实际落地**：读侧谓词以 `version.book_id = :bookId` 聚合该书**全部版本**的 grants（任一版本有 class grants 即视为受限）；写侧先删本书所有版本的 class grants，再写入当前版本，使状态规范化。

**保留理由（两个都是真实的 fail-open 口子）**：

1. 纯版本级语义下，教师把 v1 限定给 B 班，之后这本书导入 v2，v2 没有 grants 行 → 判定为「无 grants = 全组织可见」→ **全校突然都能看到**，且无任何提示。这正是本项目反复栽跟头的那类静默失效。
2. `getPage` 允许显式传 `?versionId=` 指定旧版本，纯版本级会留下「拿旧版本号绕过」的口子。

书级聚合后，B 班在版本升级后仍保有访问权（grants 行还在 v1 上，谓词按 book 聚合仍能命中），语义连续。且 UI 本来就是按「书」操作的，与用户心智一致。

**记入交接**：这是本期唯一一处偏离契约字面表述的地方，偏离方向是收紧。

**附带记录一个已知行为**：`BOOK_HAS_GRANTS_SQL` 判断「有没有 grants」时**不区分 `grantee_type`**，而「是否授权给我」只认 `grantee_type='class'`。因此若将来有人插入非 class 类型的 grant 行（如单个学生粒度），该书会对所有学生不可见、仅管理角色可见。方向是 fail closed（安全），但**将来实现学生粒度授权时必须同步改这条 SQL**，否则会表现为「书突然从所有学生书架消失」。

### 决策 P4-18：`GET /books/:bookId/visibility` 收紧为管理端专用

实施方将该接口对学生一律返回 404（无论该书对他是否可见），权限动作仍是 `book.read`，未新造动作。**主控裁决保留。**

理由：班级授权名单里含别班的 class id 与班名，学生没有任何理由看到；返回 404 与「不可见书」同一响应，不产生新的存在性差异。这是收紧不是放宽。

**这条要同步给守卫测试方**——若按「学生 + 可见书 → 200」去写会与实现冲突。以本决策为准。

### 决策 P4-19：学生自有对象的写路径本期不加 grants 过滤

实施方报告：`POST /reading/library/favorites|bookmarks|excerpts|annotations`、社区投稿、AI 会话创建这几条**写**路径仍只校验「本组织 + published」，未过 grants。**主控裁决：本期不动。**

理由：

1. **不构成内容泄露**——page / asset / AI 三条内容路径已经封死，这些写路径拿不到书的任何内容。
2. 要利用它需要先持有该书的 `bookVersionId` UUID，而这只能来自该书曾对他可见的时期（或下方 D-21 那条社区路径）。
3. 给这些路径加过滤，等于对学生**既有的**喜欢/书签/摘录做级联失效——正是 B-4 明确不要的那类级联。

**代价（如实记录）**：收窄可见范围后，学生已有的书签、摘录里仍会显示这本书的书名。属残留，不是新增泄露（他此前本就知道书名）。

### 决策 P4-20：社区引文的可见范围泄露登记为缺陷，本期不修

主控独立核查发现（不在实施方报告范围内）：`server/domains/community/index.js` 的 `getPost` 返回 `quote: { bookId, page, text }`，`quote_text` 最长 2000 字且经校验确为书页原文，**读取时没有任何可见范围过滤**。

因此存在这条链：B 班学生引用一本限定给 B 班的书投稿 → 帖子过审、范围为校级 → **A 班学生读到该书原文片段**。这是真实的内容泄露，不只是存在性泄露。

**本期不修，登记为 D-21。** 理由：① 触发需要人工审核放行，不是自动路径；② 社区不在 B-4 点名的四个入口内；③ 正确的修法要先定产品语义——投稿时就拦、还是读取时过滤、已过审的旧帖要不要追溯处理——这属于产品裁决，不该在验收前夜顺手塞进最高风险的那段代码里。

### 决策 P4-22：F-1 越权当期收口——授权范围校验补上删除侧

独立验证方（T4.7）实测打穿了一条越权链，主控裁决**当期收口**。

**攻击链（真实 HTTP 实测）**：校长把某书限定给 C 班（在 A 班班主任授权范围外）→ A 班班主任显式请求授权给 B 班被正确 403 → 改发 `{"scope":"organization"}` 得到 **200**，书对全组织打开，B 班拿到刚被拒绝的访问权，校长给 C 班的 grants 行被一并删除。

**根因**：`authorizedClassIdSet` 只校验**新增的班级集合**，对「放开到全组织」和「删除范围外班级的既有 grants」都不设限。于是这条校验在放宽方向上等于不存在。

**裁决理由**：核心矛盾是「你不能对一个别班做的事，可以对所有班一起做」。这个不对称在任何权限模型下都站不住，不需要等更大的权限模型裁决就可以先收口。

**收口规则**：在「新增集合必须在授权范围内」之外，补上对称的删除侧校验——移除某班的 grants 时该班也必须在操作者授权范围内。

**一个必须豁免的边界**：`listAuthorizedClasses` 只返回 active 班级，所以指向**已停用/已删除**班级的悬空 grants 不在任何人的授权集合里（**包括校长**）。若不豁免，这类书将永久无法修改可见范围。因此删除侧校验**只对当前仍 active 且属于本组织的班级生效**。

**保住的主用例**：书无 grants 时，班主任仍可把它限定到自己班；自己设的限定，自己可以撤销回全组织。

### 决策 P4-23：F-4 的修法是修好逃生通道，不是收敛 HAS_GRANTS

独立验证方发现：手工插入一行非 class 类型的 grant 后，该书对所有学生消失、`GET visibility` 却报告 `scope: 'organization'`、且 `PUT {"scope":"organization"}` 删不掉它（DELETE 只删 class 类型），书**无法恢复可见**。今天没有 HTTP 路径能造出这种行。

验证方建议把「有没有 grants」的判定也收敛到 `grantee_type='class'`。**主控不采纳这个方向**——那会把「出现未知类型 grant」从 fail closed（书对学生不可见，安全方向）变成 **fail open**（书对全组织可见，危险方向）。

**采纳的修法**：`scope=organization` 的 DELETE 清除该书全部版本的**全部** grants 行，不限类型，使逃生通道在任何情况下都有效；`BOOK_HAS_GRANTS_SQL` 保持 fail closed 不变，并就地加注释说明这是有意的、以及配套前提。

### 决策 P4-24：F-2 / F-3 登记为缺陷，本期不修

- **F-2**（`GET /assignments` 向未授权班学生泄露书名与 bookVersionId）→ 登记为 **D-22**。不在 P4-19 的豁免清单内（那条豁免的是学生自有对象的写路径与已有书签摘录，阅读安排是教师创建的对象），故按新口子登记。只泄露元数据不泄露正文。
- **F-3**（`POST /reading/lease` 不过可见范围与发布状态）→ 登记为 **D-23**。**不修的关键理由**：租约 TTL 与续租路由属项目冻结契约，是 D-11 / D-15 / D-17 三次复发的重灾区，在验收前夜动它风险过高。且它不泄露正文。

两者应当一并规划：D-22 是 D-23 的前置（学生正是从阅读安排里拿到 `bookVersionId` 的），单修一个意义不大。

### 已知不一致（待产品负责人裁决，本期不动）

### 决策 P4-21：阅读安排完成率属既有 UI，不在「完成度」冻结契约射程内，还原

## 六、L3 真实数据实测的处置（2026-08-18）

### 更正：`express` / `dotenv` 缺失是误报，不存在该风险

L3 报告以【高】级别提出「`express` 与 `dotenv` 既不在 `node_modules` 也不在 `package.json` 依赖里，验收当天一旦重启后端就起不来」。**主控核实后判定为误报，不需要任何处置。**

它只检查了仓库根的 `node_modules` 与根 `package.json`。本项目前后端**分开声明、分开安装**：`server/package.json` 明确声明了 `express@^4.21.2` 与 `dotenv@^16.4.5`，且两者都实际装在 `server/node_modules`（实测 express 4.22.2、dotenv 16.6.1）。README 也写明要分别执行 `npm install` 与 `npm --prefix server install`。后端可正常重启。

顺带确认了 L3 自行推断的 express 大版本正确：声明确为 4.x，与 `server/app.js` 里 `app.get('*')` 的用法一致（该写法在 express 5 的 path-to-regexp v8 下会启动失败）。

**留档理由**：该误报以最高严重度写在归档报告里，若不就地更正，后续读者会据此在验收当天做无谓的紧急处置。**同时是一条方法教训**：多包仓库里判断依赖缺失，必须逐个包检查其自身的 `package.json` 与 `node_modules`，不能只看仓库根。

### 教师 / 校长调 `GET /reading/library` 返回 403 属预期，非缺陷

L3 提出待确认。**主控裁决：设计如此，不改。** 该接口是**学生阅读对象**的书架投影，角色闸门与可见范围无关——L3 自己已用「book-049 恢复全组织可见后仍是 403」排除了相关性。教师侧的书库入口是控制台的 `GET /books`（实测教师 200、49 本、不受 grants 过滤）。两条路径本就分开。

## 七、守卫测试暴露的契约留白：逐条裁决（2026-08-18）

以下均为独立验证方实测出的真实行为，契约未写明。除已单独成节的 F-1 / F-4（见 P4-23、P4-24 前后）外，逐条裁决如下。**本节全部为「记录现状、本期不动」**，理由统一：它们都不构成内容泄露，且都有可用的恢复路径。

### 停用班级的 grants：管理端显示与学生实际可见性不一致（本期不动）

班级 `status='disabled'` 后，grants 行保留，但 `findUserScope` 只认 active 班级，于是**该班学生失去这本书**；而 `GET visibility` 仍把这个已停用班列在授权名单里（含班名），`GET /classes` 不再列它，再次授权给它返回 403。

**不动的理由**：① 重新启用班级即自动恢复；② `scope=organization` 逃生通道全程可用；③ 不泄露任何内容。**但它是 F-1 悬空豁免规则的邻接面**——F-1 收口时特意把「指向非 active 班级的 grants」排除在删除侧校验之外，正是为了避免书永久无人可改。两者口径一致，不要单独改一边。

### 孤儿学生（无任何班级成员关系）：与停用班学生表现一致（契约推论成立）

无 `class_memberships` 的账号：无 grants 的书可见，任何有 grants 的书一律 404。符合 B-4 推论，无需处置。

### grants 指向已删除班级：书对所有学生不可见，管理角色仍可见（本期不动）

`classes` 行被删后 grants 悬空，书对**所有**学生不可见（谁都不在这个班里），`GET visibility` 返回 `{ id, name: null, gradeId: null }`，`scope=organization` 能清干净。fail closed 方向正确，逃生通道有效。

### 伪造 `X-Workspace-Id` 的失败口径是 403 而非 404（确认该框定）

换到非本人成员的工作空间时，请求在 `requireWorkspace` 就被拒，返回 403 `PERMISSION_DENIED`，未走到书籍查询。**主控确认这个框定成立**：验证方已实测它对「存在的书」与「不存在的书」**同码同文案**，因此不构成存在性泄露，属于与「不可见书必须 404」不同的失败类别，不要求统一成 404。

### 独立验证方的守卫文件被改动三条用例：授权来源与逐条理由

`tests/server/http/book-visibility-guard.test.js` 是独立验证方（只写测试、不改实现）的资产，原则上实施方不得触碰。F-1 / F-4 收口后它有 3 条用例需要更新，**全部经主控逐条授权**，记录在此以便追责：

| 用例 | 原标题前缀 | 授权理由 |
|---|---|---|
| F-1 利用链 | `【攻击成功·待裁决】` | 验证方自己标了「待裁决」，主控裁决收口，用例随裁决结果从「断言攻击成功」改为「断言被 403 挡住」。 |
| F-4 逃生通道 | `【现状记录·待裁决】` | 同上。断言的正是缺陷本身（`organization` 删不掉非 class 行、书仍不可见），修完必然变红，无第三条路。grants 行数 `1`→`0`、`assertInvisible`→`assertVisible`。**`GET visibility` 仍报 `organization` 那两条断言未动**——快照口径没改，那处谎报仍在。 |
| `【攻击面 4.12/4.13/4.14】` 授权范围逐层校验 | 无标记 | **这条最需要说明**：它没被标成待裁决，是验证方当成「grade 范围正向能力」写的，但它第 6 步的前置状态是书已被限定到一年级 A/B 班，于是二年级主任授权 C 班的同时构成一次跨范围移除——与主控要求返回 403 的场景**结构完全同构**。修法采纳「在该步前插入一次校级 `organization` 归零」，而非把期望改成 403：**保住了用例作者检验正向能力的原意**。 |

**为什么不是「测试挡路就改测试」**：三条都做了正向能力的独立确认——二年级主任在**无 grants** 的书上授权本年级班仍是 200（实测），证明收紧没有误伤 grade 范围的正向授权，坏掉的只是那一步依赖的前置状态。新规则本身另由**新文件** `tests/server/http/book-visibility-revoke-guard.test.js` 的 7 条用例正面覆盖（含「年级范围操作者不能连带移除别年级既有授权」→ 403、`details.classIds` 为 `[classA, classB]`），覆盖率不减。

**流程上的教训**：新增用例应放进新文件而非混写进验证方的文件，否则「哪条断言是谁写的」不可查。本轮实施方主动这么做了（7 条新用例进新文件，只动被点名授权的那 1 条），这个做法应固化为规矩。

### `scope=organization` 同时带 `classIds: []` → 200（确认为合法）

空数组视为未提供，200 通过；带非空 `classIds` → 422。契约只说「拒绝」未区分空数组。**主控确认前者合法**：`{scope:'organization', classIds:[]}` 是前端「恢复全组织可见」的自然请求形态（L3 实测校长即以此形态成功恢复），拒绝它会无谓地增加前端负担。
